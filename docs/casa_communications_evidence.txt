SenderWho - CASA Communications and Cryptography Evidence
Prepared: 12 October 2026
Basis: current source review. No SSL Labs scan or production key-management
inspection was performed while preparing this document. No secrets are included.

4.1.1 and 4.1.2 - Required TLS evidence

The app's default production API is https://senderwho.com/api/v1. A release build
may override this with SENDERWHO_API_URL. Scan the hostname of the actual API used
by the assessed release, plus other publicly exposed application HTTPS hostnames
in the agreed assessment scope.

Use https://www.ssllabs.com/ssltest/ and enter the hostname without a URL scheme
or path. Wait for the completed report, review all reported endpoints, and export
the full report to PDF using the browser's Print / Save as PDF function. Upload
the same report for 4.1.1 and 4.1.2 when both rows concern the same hostname.
Include additional reports if the application uses other public hostnames.

Review the protocol, cipher and certificate results; a grade alone does not
establish every requirement. Do not claim TLS 1.0/1.1 are disabled, that all
certificates are trusted, or that a particular grade was obtained before reading
the completed results. SSL Labs assesses public server TLS, not every internal
database or outbound connection.

Source transport controls: release app configuration requires an HTTPS API URL;
Android disables cleartext traffic; iOS disables arbitrary transport loads;
production backend middleware rejects non-HTTPS requests. Provider OAuth/API
endpoints and unsubscribe requests use HTTPS. These are supporting controls,
not substitutes for the required TLS report. Private/local database transport
exceptions exist in deployment configuration and must be disclosed if used in
the assessed deployment.

4.1.3 - Cryptographic operations

A. Provider credentials and OAuth PKCE verifier encryption

Algorithm: AES-256-GCM using Node.js crypto.
Key: 32 bytes (256 bits), supplied through server runtime configuration as
Base64-encoded key material. Production validation requires a valid key ring
and active key identifier. The deployment instructions prescribe generating a
32-byte random encryption key with openssl rand -base64 32. Actual production
key generation has not been independently confirmed.
IV: a fresh 12-byte (96-bit) IV generated by crypto.randomBytes for each encryption.
Authentication: GCM authentication tag; the current encryption code uses the
Node.js default 16-byte tag. Version-2 records also authenticate a context string
using additional authenticated data (AAD), including the provider/account
context for provider tokens or a separate context for PKCE verifiers.
Storage: ciphertext, key ID, IV and authentication tag are stored in a versioned
record. Secret encryption keys are supplied separately through server runtime
configuration, rather than included in the ciphertext.
Rotation: TOKEN_ENCRYPTION_KEYS and TOKEN_ENCRYPTION_ACTIVE_KEY_ID support a key
ring. Provider-token services detect older versions/key IDs and re-encrypt tokens
with the active key when accessed or refreshed. Legacy AES-GCM records remain
readable when the legacy key is configured; those records lack the v2 AAD binding.
Expiration: the code does not enforce automatic encryption-key expiration or a
rotation interval. Operational rotation, old-key removal and key-storage access
permissions require confirmation from the deployment owner.
Evidence: server/src/common/security/token-encryption.service.ts;
server/src/providers/google-token.service.ts and corresponding Microsoft/Yahoo
token services; server/src/common/config/validate-environment.ts.

B. Hashing and secure random values

Algorithm: SHA-256 for application refresh-token hashes, OAuth exchange-secret
hashes, nonce hashes and PKCE challenges. SHA-256 is also used for idempotency
request fingerprints, throttling identifiers, device identifiers in security
logs and migration checksums. No secret key or IV is used by these hash operations.
Refresh tokens are generated from 48 random bytes; OAuth exchange secrets and
nonces use 32 random bytes; PKCE verifiers use 48 random bytes. Values use
crypto.randomBytes and Base64url encoding. Stored secret hashes are compared
using crypto.timingSafeEqual after verifying equal buffer lengths.
These hashes protect high-entropy tokens; the application does not store user
passwords and does not use SHA-256 as a password-storage scheme.
Refresh-token rotation, session revocation and expiry are controlled by the
session implementation; these should be described separately from key expiry.
Evidence: server/src/auth/auth.service.ts; server/src/common/security modules.

C. MAC/HMAC for application JWTs and OAuth state

Algorithm: HS256 (HMAC-SHA-256), the current jsonwebtoken signing default used
by the application's JwtModule. The application does not explicitly set a
different signing algorithm in its signing configuration.
Key: server-side JWT_SECRET; startup validation requires at least 32 characters.
Deployment instructions prescribe a cryptographically random secret generated
with openssl rand -hex 64 (64 random bytes before hex encoding). The actual
production secret entropy and generation procedure have not been inspected.
IV: not applicable to HMAC.
Storage: signing secret supplied through runtime environment/configuration.
Expiration: access JWTs default to 15 minutes and production validation rejects
longer durations. OAuth state expires after 10 minutes. These are token expiry
periods, not signing-key expiry periods. No automated signing-key rotation or
key-expiry schedule is implemented in the reviewed code.
Evidence: server/src/auth/auth.module.ts; server/src/auth/auth.service.ts;
server/src/common/config/validate-environment.ts; jsonwebtoken signing default.

D. Provider identity signatures when those integrations are enabled

Microsoft identity tokens: RS256 verification using provider-published RSA public
JWKs fetched over HTTPS, selected by key ID. Private signing keys and their
generation/rotation are controlled by Microsoft, not SenderWho. The app does
not impose an explicit RSA modulus-size check in the reviewed code.
Yahoo identity tokens: ES256 verification using provider-published P-256 public
JWKs fetched over HTTPS, selected by key ID, algorithm and curve. Private keys
and their generation/rotation are controlled by Yahoo, not SenderWho.
These verification operations use SHA-256 and no application-generated IV.
Google identity validation: the reviewed app uses Google's HTTPS tokeninfo
endpoint and validates issuer, audience, timestamps, subject and nonce claims.
Evidence: server/src/auth/auth.service.ts provider identity validation methods.

4.1.4 - Failure behavior and remaining limitation

The reviewed token encryption uses authenticated GCM rather than CBC/padding.
decrypt() authenticates the stored context and tag, and only returns plaintext
after decipher.final() completes successfully. Invalid ciphertext, mismatched
context/tag or unavailable keys raise an error; there is no plaintext fallback.
JWT verification errors are converted by JwtAuthGuard into a generic unauthorized
response, and invalid OAuth state is rejected. Invalid Microsoft/Yahoo signatures
or identity claims are also rejected. The HTTP security logging interceptor logs
error types and metadata rather than full token values or raw exception text.

Full uniform, generic failure handling is NOT established by this source review.
TokenEncryptionService has distinct format/key/configuration errors, including
a ServiceUnavailableException whose message contains the requested key ID. That
exception can propagate through provider-token API paths, so it must not be
claimed that every cryptographic error is indistinguishable to clients.
The code also has no local wrapper that normalizes all encryption/decryption
failure responses. Review/remediation and dynamic confirmation are required
before asserting complete compliance with the error-disclosure requirement.

Evidence: server/src/common/security/token-encryption.service.ts decrypt() and
key lookup; server/src/auth/jwt-auth.guard.ts verification catch;
server/src/common/security/security-logging.interceptor.ts.
